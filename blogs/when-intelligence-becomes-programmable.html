01

The Pattern Behind Every Wave

Technological revolutions follow a familiar pattern. An enabling infrastructure appears, capability becomes democratized, network effects compound, applications cascade, and incumbents are disrupted. So I will dare to compare today’s Transformer-backed Generative AI, and the ecosystem growing around it through harnesses and agentic AI, with the revolutions that came before. History does not merely rhyme in technology. It compounds.

The Industrial Revolution multiplied human muscle. Personal computers made computing personal. High-level languages and modern compilers made software expressive. The internet and the dot-com boom made information free to move. Distributed systems like Search, Gmail and Maps made scale reliable. Smartphones made the computer disappear into everyday life.

Every one of these waves brought excitement, skepticism, disruption and anxiety in its early days. Each shook its industry and, over time, produced positive disruption for people and businesses. Each built on the previous one and became the foundation for the next.

So instead of only asking how powerful AI will become, I find a different question far more interesting: what happens when intelligence becomes programmable, scalable, and increasingly inexpensive? From first engineering principles, every major wave made a previously scarce capability cheaper, then more accessible, then easier to build upon.

The biggest impact of a technological revolution is not necessarily the technology itself. It is everything that gets built on top of it.

And we may still be very early in that story.

02

The Agent Can Generate the Code

Brilliant. And yet I still see many software engineers complaining about the quality of code generated by AI agents. That is often the first stage of grief: denial.

The real issue is rarely that an agent cannot write code. It is that teams ask an agent to write code before the team has made the decisions that make code correct, safe, maintainable and reviewable. AI has made implementation dramatically faster. But specifying intent, choosing an approach, resolving ambiguity, approving scope, verifying behavior and accepting accountability remain human-paced activities.

That is where the opportunity lies.

03

The Missing Layer: Change Management

High-level SDLC diagrams are useful, but they do not tell an AI agent what “correct” means for this ticket, in this codebase, under these constraints. That is a different layer, and it is the one that is missing.

Agent = Model + Harness
The model provides reasoning and generation.
The harness provides instructions, tools, guardrails, tests, feedback loops, observability and, critically, the decisions that constrain the work.
The framing comes from Google’s 2026 whitepaper on the new SDLC with vibe coding.

A change-management workflow is part of that harness. A note on the term: I mean it in the engineering sense of governing one change through its lifecycle, not the ITIL sense of organisation-wide change enablement. ITIL asks whether a change may enter production. This asks whether a change was decided, planned, built and verified as agreed.

Concretely, the workflow tells the agent what problem is being solved, which approach was chosen and by whom, what is in scope and what is explicitly out, which assumptions must be validated, which questions block implementation, what tests prove the change works, and when a human must stop the machine and decide.

The tell

Without this layer, AI-generated code can look impressive while quietly encoding the wrong assumption.

04

The Real Bottleneck Is Not Code Generation

Many teams discover the same recurring gaps. Assumptions behind generated code never reach the tracker. Changes arrive at review without a named person having approved the approach or scope. Implementation begins while the approach is still being debated. Decisions live in Slack threads, meetings and people’s heads rather than in the ticket.

Then the second half. Plans drift from the code that was actually written. Open questions have no owner or severity, so they resurface during code review. Deferred work disappears, only to return later as an incident. Design problems are discovered late, in review rather than before implementation. And the reports that do exist are long, generic, code-heavy “AI output” that reviewers and leaders cannot use.

These are not model-quality problems alone. They are process and governance problems.

When implementation becomes cheap, the scarce asset becomes the record of why a change was made, by whose decision, and against which requirements.
05

A Tracker-Anchored Workflow

One practical approach is to treat a tracker ticket as the unit of governance. Each stage of the change produces a durable, structured record on the ticket. The next stage reads that record before proceeding. The agent does the mechanical work; humans make the decisions that require judgment.

Stage
Question answered
Output
Assess
What are the options and which do we recommend?
Requirements, constraints, approaches, risks, open questions
Confirm
Which approach was chosen, by whom, and why?
Named decision, scope, assumptions, deferred items
Plan
What exactly will be built and how will it be proven?
Work items, tests, acceptance mapping
Implement
Build the agreed change
Code, tests, gates, implementation report
Verify
Is this the change we agreed to build?
Plan and code conformance, blockers, verdict
Review
Is the code ready for external review?
Author self-assessment
Submit
Commit and push the reviewed change
Commit, changelog, submitted patch
Incorporate
How do we address external review?
Fixes, replies, verification, next patch

The agent can prepare options, draft plans, run tests, apply gates, generate commit messages and summarize evidence. But approach selection, approval, scope changes, Critical questions, commits and pushes should wait for a named person.

The principle

Humans decide; agents implement.

06

Why This Matters

This is not bureaucracy for its own sake. It is how teams convert AI speed into reliable engineering throughput. Look at the same team, with and without a shared record.

Without a shared record
With a shared record
Engineers re-explain the approach at every review
Assumptions become challengeable
Reviewers cannot see what was decided or by whom
Questions get owners and severity
Leads cannot tell which questions are open, or how serious
Deferred work gets a destination ticket
Support and maintainers cannot recover the intent behind a change
Reviewers compare code against the agreed design
Fast code generation gets mistaken for fast delivery
Accountability is visible rather than implied
The agent leans on chat history
The agent has a stable source of truth

That last row is the one I care about most as a builder. A chat history is a lossy, private, perishable thing. A ticket is none of those.

07

The Shift in the Engineer’s Job

The engineer’s job does not disappear. It moves up the abstraction ladder. Instead of spending most of their time translating intent into syntax, engineers increasingly spend it defining the problem precisely, identifying constraints and risks, comparing approaches, making and recording decisions, designing verification, reviewing evidence rather than just diffs, and owning the outcome.

In other words, the engineer becomes the designer and governor of the system that produces software, not merely the author of every line.

08

What Will Become Obsolete

Some specific tools, prompts, workflows and agent capabilities will certainly become obsolete. That is normal. Compilers improved. Frameworks changed. Cloud platforms evolved. Mobile ecosystems matured. The underlying capability persisted and became the foundation for the next layer. The same will happen here.

The durable ideas are likely to be these: explicit intent, recorded decisions, named accountability, verification before review, guardrails around autonomous action, and a shared, queryable record of why software changed. The exact implementation may change. The need for it will not.

The Takeaway

Agentic AI can generate code. That is no longer the hard part. The hard part is ensuring the code represents a decision a responsible human actually made, against requirements that were understood, with assumptions that were examined, and with evidence that the result behaves as intended. That is the work of change management.

In an era when intelligence becomes programmable, scalable and inexpensive, the teams that win will not simply be the ones that generate the most code.

They will be the ones that can trust what they ship.
